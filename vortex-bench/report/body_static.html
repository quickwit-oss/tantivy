Méthode

Le bench est une copie de benches/agg_bench.rs (vortex-bench/benches/agg_bench_vortex.rs). Les requêtes et le générateur de données sont inchangés : 1 000 000 de documents, quatre entrées (full, dense, sparse, multivalue) plus les index à 100 et 1000 segments. Seule différence côté index : le VortexPlugin est enregistré à la création, donc chaque segment porte un fichier .vortex en plus du .fast. Les trois variantes lisent donc exactement les mêmes segments.

Chaque requête est exécutée en trois variantes :

  • columnar : le chemin normal de tantivy (ce que mesure agg_bench).
  • opaque : les mêmes colonnes tantivy, mais enregistrées dans le ValueSourceRegistry derrière un wrapper qui renvoie None pour as_column(). C'est le groupe témoin : il paie la même pénalité « source enregistrée » que Vortex, avec le codec tantivy.
  • vortex : les colonnes du fichier .vortex, enregistrées de la même façon.

Le rapport opaque / columnar isole donc le coût de l'abstraction (fast paths perdus), et vortex / opaque isole le coût du stockage Vortex lui-même. Leur produit donne vortex / columnar.

Les trois variantes d'une requête sont dans le même groupe binggan, donc entrelacées (32 itérations de groupe, nombre d'itérations par bench auto-détecté, médiane). Les ratios sont calculés à l'intérieur de chaque passe, puis on prend la médiane sur les passes. La colonne « dispersion » est l'écart max − min des ratios vortex / columnar entre passes, rapporté à la médiane ; les requêtes au-dessus de 10 % sont marquées ↯ et ont été relancées.

Les champs enregistrés sont tous les fast fields non-JSON : score, score_f64, score_i64, timestamp, timestamp_26_bits et les sept champs texte. Le champ JSON json.mixed_type reste toujours lu par le columnar.

Machine. sysctl indique un Apple M4 Max (12 cœurs performance + 4 efficacité, 64 Go), sous macOS 26.6.2, et non un M5. Les benchs sont mono-thread ; rien d'autre ne tournait pendant les passes (les compilations et les autres mesures ont été faites entre les passes).

Intégration

Tout le code est dans le crate autonome vortex-bench/ (son propre workspace, pour ne pas ajouter l'arbre de dépendances Vortex au workspace tantivy). Aucune modification de tantivy n'est nécessaire pour la phase 1.

Écriture : le plugin de segment

VortexPlugin implémente SegmentPlugin avec l'extension vortex. Il n'accumule rien pendant l'indexation : les plugins custom sont sérialisés et mergés après les built-ins, donc il relit le .fast du segment et convertit chaque colonne non-JSON de type u64, i64, f64, date ou texte. Le même code sert pour serialize et pour merge.

  • Les valeurs sont stockées dans leur type logique (u64, i64, f64, timestamp nanosecondes en type extension temporel), pour laisser à BtrBlocks ses schémas spécialisés (ALP pour les flottants, DateTimeParts pour les dates).
  • Les colonnes texte stockent les ords (u32) du dictionnaire sstable de tantivy. Le dictionnaire n'est pas dupliqué : la ValueSource le récupère dans le fast field au moment de la requête. Une variante « strings natives » est mesurée à part pour le volume.
  • Cardinalité : Full devient un tableau non nullable, Optional un tableau nullable, Multivalued une List.
  • Chaque colonne est un fichier Vortex autonome écrit avec la stratégie par défaut de vortex-file 0.88 (repartition en blocs de 8192 lignes avec statistiques de zone, coalescence vers ~1 Mo non compressé, compression BtrBlocks). Le fichier .vortex est la concaténation de ces fichiers, alignés sur 64 octets, suivie d'un pied JSON.

Lecture : la ValueSource

  • Un VortexSegmentCache partagé par tous les providers ouvre le .vortex une fois par segment (copie alignée, open_buffer, scan) et garde les chunks compressés. C'est l'équivalent de ce que ferait un SegmentReader ; tantivy ouvre ses colonnes à chaque requête, mais pour un coût négligeable (mmap + en-tête).
  • Chaque collecteur reçoit sa propre VortexValueSource. load_block découpe le bloc de docs en runs par chunk, décompresse le chunk en tableau canonique (execute::<PrimitiveArray>), puis convertit vers le mapping u64 monotone de tantivy en recopiant les valeurs demandées.
  • Les 8 derniers chunks décompressés sont gardés (LRU). La première version n'en gardait qu'un ; voir l'effet de ce choix.
  • bounds() renvoie le min / max calculé à l'écriture, ce qui garde le chemin « dense » des histogrammes. as_column() renvoie None : les fast paths qui en dépendent sont perdus (voir Fast paths).

Non supporté par une source enregistrée

Ces requêtes échouent en opaque comme en vortex, par conception actuelle de tantivy : multi_terms et composite refusent les sources enregistrées, top_hits exige la colonne physique, et missing n'est pas supporté sur une source texte calculée. Elles n'apparaissent qu'en columnar dans les tableaux.

Volume des fichiers

La comparaison porte sur les colonnes elles-mêmes : la colonne tantivy (valeurs + index optional / multivalué, sans le dictionnaire) contre le fichier Vortex de la même colonne. Le fichier .fast contient en plus les dictionnaires sstable (que la variante Vortex réutilise) et la colonne JSON, d'où l'écart entre les deux dernières colonnes du tableau.

Ce qu'il faut retenir

  • Colonnes pleines, mono-segment : match nul. 25,13 Mo contre 25,04 Mo (−0,4 %). Les deux formats font du bitpacking sur les mêmes données : score tient en 20 bits par valeur dans les deux cas (2,44 Mo). Vortex gagne 8 % sur timestamp grâce à DateTimeParts, perd 4 % sur timestamp_26_bits, et ALP-RD fait jeu égal sur score_f64 (6,92 contre 7,00 Mo, des log-normales sans structure décimale).
  • Optional et sparse : Vortex gagne. −6 % en dense (un seul doc sans valeur : la validité se compresse presque à rien), −30 % en sparse (encodage sparse + sequence pour les positions).
  • Multivalué : −34 %, mais sur un cas favorable. Dans ce jeu de données un seul document a deux valeurs : les offsets de liste forment une suite arithmétique que Vortex encode en vortex.sequence (quasi gratuit). Côté tantivy, l'index multivalué de single_term pèse 1,5 Mo pour 1 M de docs alors que les valeurs elles-mêmes ne coûtent rien ; c'est à regarder séparément dans le codec de tantivy. Sur des données réellement multivaluées, l'écart serait plus faible.
  • Petits segments : Vortex perd nettement. +15 % à 100 segments, ×2,2 à 1000 segments. Chaque fichier Vortex a un coût fixe d'environ 2 ko (footer, dtype, layout, statistiques de zone) ; ici il y a un fichier par colonne et par segment, soit 12 000 fichiers pour l'index à 1000 segments. Un seul fichier Vortex par segment (struct de colonnes) réduirait cette part, voir la mesure.
  • Strings natives : beaucoup plus gros. Stocker les chaînes dans Vortex plutôt que les ords + le dictionnaire tantivy coûte 14,5 Mo contre 10,9 Mo pour text_all_unique_terms et 6,1 Mo contre 2,26 Mo pour text_many_terms (150 000 termes). Pour les colonnes à faible cardinalité, l'encodage dictionnaire de Vortex fait jeu égal. Garder le dictionnaire sstable reste le bon choix.
  • Format fichier : en mono-segment, le fichier Vortex n'ajoute rien de mesurable par rapport au tableau compressé en mémoire (25,04 contre 25,06 Mo), les statistiques de zone sont compensées par une compression par chunk.
