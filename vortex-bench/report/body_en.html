1. Context and question

tantivy aggregations read their input from fast fields, which live in the columnar component of each segment (the .fast file). Vortex is a columnar file format and in-memory array library built for analytical scans, with a large catalog of lightweight compression schemes and an adaptive compressor. The question is simple: if the columns that feed aggregations were stored as Vortex arrays, what would happen to query time and to file size?

Answering it requires two pieces of plumbing that tantivy recently gained:

  • the segment plugin system (SegmentPlugin), which lets external code write extra files into a segment, at commit and at merge time;
  • the ValueSource abstraction, which lets an aggregation read the values of a field from something other than the physical tantivy column.

The experiment uses both: a plugin writes a Vortex copy of every non-JSON fast field into a .vortex file, and a ValueSource implementation serves those values to the unmodified aggregation code. The whole agg_bench suite then runs against the tantivy columnar and against Vortex, on the same segments.

The report is written for a tantivy developer who has never looked at Vortex. Sections 2 to 4 explain the two systems and how their concepts line up. Section 5 describes the integration. Sections 6 and 7 hold the measurements. Section 8 explains, without numbers, how the reader was made fast on selective queries.

Setup. Apple M4 Max (12 performance cores, 4 efficiency cores, 64 GB), macOS 26.6.2, rustc 1.100 nightly, release profile. tantivy at commit 678343990, Vortex 0.88.0 (crates.io), binggan 0.17. All benchmarks are single threaded. Indexes are generated by the unmodified agg_bench generator: 1,000,000 documents per index.

2. The tantivy side

This section is a refresher, but it focuses on the properties that matter for the comparison: how values are addressed, how they are compressed, and which shortcuts the aggregation code takes.

2.1 Segments, components and plugins

A segment is an immutable set of files sharing a UUID and differing by extension: postings (.idx, .pos, .term), field norms, the doc store, fast fields (.fast), deletes. Since the plugin refactoring, every built-in component is itself a SegmentPlugin. A plugin declares the extensions it owns, creates a PluginWriter for each new segment (fed with every document, then asked to serialize) and implements merge, which receives the source segment readers and the doc id mapping.

Two properties of the plugin system make this experiment cheap:

  • Ordering. Built-in plugins serialize and merge first, custom plugins afterwards. A custom plugin can therefore open the freshly written .fast file of the segment it is building and derive its own file from it, both on commit and on merge.
  • Fail-closed metadata. The index metadata records the custom extensions it requires (persisted_custom_extensions). Opening a writer without re-registering the plugin fails instead of silently producing segments without the extra file.

2.2 The columnar: columns, indexes and values

The .fast file is one ColumnarReader. Columns are keyed by name and ColumnType (a JSON field can have several columns with the same path and different types). A DynamicColumnHandle opens a typed column lazily, by slicing the memory-mapped file.

A column is Column<T> = ColumnIndex + Arc<dyn ColumnValues<T>>. The split matters: values are stored densely by row id, and the column index maps doc ids to row ids.

Cardinality::Full
Every doc has exactly one value; row id = doc id. No index at all.
Cardinality::Optional
Every doc has at most one value. The OptionalIndex splits the doc id space into blocks of 65,536 docs. A block with many values is stored as a bitset with rank metadata, a block with fewer than 6,144 values as a sorted list of 16-bit offsets. Turning a doc id into a row id is a rank query.
Cardinality::Multivalued
An optional index of the docs that have values, plus a column of start offsets (one per doc with values), itself compressed with the bitpacked or linear codec. The values of doc d are rows start[d]..start[d+1].

Values are stored as u64 through a monotonic mapping: i64 flips the sign bit, f64 uses the usual sign-magnitude trick, dates are their timestamp in nanoseconds (truncated to the field precision) mapped like an i64, IP addresses go through a compact-space mapping. Order is preserved, so min / max and range filters work on the mapped values. The aggregation code works on these mapped u64 values internally.

A ColumnValues implementation is chosen per column by estimating the encoded size with each candidate codec:

Bitpacked
Subtract the minimum, divide by the GCD of the values, bitpack with a fixed width.
Linear
Fit a line through the values and bitpack the residuals.
BlockwiseLinear
Same, with one line per block of 512 values.

All three codecs share the defining property of the tantivy columnar: constant-time random access. get_val(row) computes a bit offset, reads one unaligned 64-bit word, shifts and masks. get_vals(rows, out) does it for a batch, and get_range(start, out) bulk-decodes a contiguous range. The cost of reading k values is proportional to k, wherever they are in the column. That is the access pattern of a search engine: the docs to aggregate come from posting lists, in increasing but arbitrary order.

Text columns (StrColumn) are dictionary encoded per segment: an sstable dictionary of the sorted distinct terms, plus a u64 column of term ordinals. Ordinals are sorted like the terms, so ordering by key or range filters on terms can work on ordinals, and the terms are only materialized at the end for the buckets that survive.

2.3 How aggregations read values

The collector hands matching docs to the segment aggregation collectors in blocks of up to 64 docs (COLLECT_BLOCK_BUFFER_LEN), in increasing doc id order. Each collector fetches the values of the block through a ColumnBlockAccessor, then updates its buckets or metrics. Bucket aggregations with sub-aggregations do not forward docs immediately: they buffer (bucket, doc) pairs and flush them to the sub-aggregations in batches (up to 2,048 docs), grouped by parent bucket. A sub-aggregation therefore receives runs of docs that are sorted within a bucket but can jump around the segment.

With a selective query, the docs of one 64-doc block are scattered over thousands of rows. With AllQuery, blocks are contiguous ranges.

2.4 The ValueSource abstraction

ValueSource is what the aggregation code reads from. Its contract, in short:

column_type()
Logical type of the values (they are returned in the monotonic u64 mapping; text values are term ordinals).
load_block(docs, values, docids, row_ids)
Loads the values of a sorted block of docs. If the source answers Full, values[i] is the value of docs[i]. If it answers Optional or Multivalued, values[i] belongs to docids[i] and docs without values are absent. Takes &mut self: a source belongs to one collector and can keep caches.
as_column()
The physical tantivy column, if any. Several fast paths require it.
bounds()
Global min / max of the values, for code that sizes something up front. Defaults to the physical column min / max.
term_dictionary()
Resolves the ordinals of a text source back into terms. Must be present for every text source.
as_physical_str_column()
The physical text column, for the features that need the whole sstable (regex include / exclude, min_doc_count: 0).

A ValueSourceProvider creates a source per segment, and a ValueSourceRegistry (passed through AggContextParams) maps field names to providers. A registered name shadows the physical field of the same name. Physical columns implement ValueSource too, so the aggregation code has a single read path.

The important detail for this study is what a registered source loses. A handful of aggregation fast paths look at as_column(), which a registered source does not provide:

  • the terms aggregation chooses its bucket storage (dense Vec with count lanes, dense Vec, paged map, or hash map) from the maximum ordinal of the column;
  • the flattened terms × histogram collector needs the raw ColumnValues of two full columns and zips them;
  • the cardinality aggregation on text uses a pre-sized bitset of ordinals when the dictionary is small;
  • the stats collector has a one-doc shortcut (values_for_doc) used under high-cardinality terms;
  • histograms and ranges use the column cardinality to pick a single-value specialization;
  • multi_terms, composite and top_hits reject registered sources altogether, and missing is not supported on a computed text source.

The benchmark therefore includes a control variant that isolates this cost (section 5.4).

3. The Vortex side

Vortex is two things at once: an in-memory array library in which arrays stay compressed and are decompressed on demand, and a file format that lays such arrays out on disk with statistics for pruning. Both halves are used here.

3.1 Logical types

Every array has a DType, its logical type, independent of how it is encoded: Bool, Primitive(ptype) (u8…u64, i8…i64, f16…f64), Decimal, Utf8, Binary, List, FixedSizeList, Struct, and Extension types layered on a storage type (timestamps, dates, UUIDs). Nullability is part of the type: a nullable u64 is a different DType from a non-nullable one. There is no global dictionary and no notion of doc id; an array is just a sequence of len logical values.

3.2 Arrays are trees of encodings

An ArrayRef is an immutable, reference-counted node with a length, a DType, an encoding (identified by an id such as fastlanes.bitpacked), some metadata, byte buffers and child arrays. The children are arrays themselves, so a compressed column is a tree: for example a timestamp column can be a datetimeparts node whose three children (days, seconds, sub-seconds) are respectively a frame-of-reference array over a bitpacked array, a bitpacked array, and a constant. Each node also carries a lazily computed statistics set (min, max, null count, is-constant, is-sorted…).

The encodings that show up in this study:

fastlanes.bitpacked
Fixed-width bitpacking in blocks of 1,024 values, using the FastLanes transposed layout so that a whole block unpacks with SIMD, without data dependencies between lanes. Values that do not fit the width are stored as patches (sorted indices + values).
fastlanes.for
Frame of reference: one reference value per 1,024-value block is subtracted, the rest is usually bitpacked.
vortex.alprd
ALP for "real doubles": each f64 is split into a left part (high bits, dictionary encoded with a tiny dictionary) and a right part (low bits, bitpacked). Left parts outside the dictionary become patches. (Plain ALP, for decimal-looking floats, turns them into integers.)
vortex.datetimeparts
Splits timestamps into days, seconds within the day and sub-seconds, each compressed separately.
vortex.constant, vortex.sequence
A single repeated value; an arithmetic sequence base + i × step.
vortex.sparse
A fill value plus patches: the right encoding when almost every row has the same value (or is null).
vortex.dict, fsst, zstd, runend, zigzag, pco…
Dictionary, string compression, run-end, zig-zag for signed integers, and others. FSST and the dictionary encoding matter for text stored natively.
vortex.list
Offsets + elements, both compressed independently.
vortex.slice, vortex.masked
Structural wrappers: a lazy view on a range of a child, and a child plus a validity bitmap.

Validity (nulls) is represented separately from values, either as a validity child or as part of the encoding (a sparse array with a null fill, for example).

3.3 Canonical forms and execution

Each DType has a canonical encoding, Arrow-like and uncompressed: Primitive (a plain buffer), Bool, VarBinView for strings, ListView (offsets + sizes + elements) for lists, Struct, Extension. Decompressing an array means executing it into a canonical form: array.execute::<PrimitiveArray>(&mut ctx). Execution is driven by an ExecutionCtx that owns allocation and dispatch; each encoding provides kernels that produce its canonical form (and fused kernels where possible, such as frame-of-reference + bitpacked in one pass).

Compute is lazy. slice, filter and take do not compute anything: take, for instance, wraps the array in a dictionary array whose codes are the requested indices, then an optimizer rewrites the tree (pushing the take into children when an encoding supports it). The work happens when the result is executed. This design shines on large batches, because a whole tree of encodings can be rewritten and executed with vectorized kernels. Its fixed cost per call (building nodes, running rewrite rules, dynamic dispatch, allocating outputs) is irrelevant for a scan over a million rows, but it dominates when the caller wants 64 values at a time.

There is also a single-value path (execute_scalar, formerly scalar_at), which returns a boxed Scalar: convenient, but not meant to be called in a loop.

3.4 The BtrBlocks compressor

Vortex does not ask the user to pick encodings. Its default compressor, modeled on the BtrBlocks paper, samples the data, estimates the compression ratio of each applicable scheme, picks the best one and recurses into the children it produces (the left parts of ALP-RD get bitpacked, the days of DateTimeParts get frame-of-reference + bitpacking, and so on). The choice is made per chunk, so different chunks of the same column can end up with different trees, as the encoding tables in section 6 show.

3.5 Files, layouts and scans

A Vortex file stores a layout tree in its footer and the array data in aligned segments. Layouts describe how a logical array is cut up on disk:

struct
One child layout per field.
chunked
A sequence of row ranges.
zoned
A data layout plus a table of statistics (min, max, null count…) per zone of rows, used to skip zones when a filter cannot match.
dict
A shared dictionary plus codes, for low-cardinality columns.
flat
A leaf: one serialized, compressed array in one segment.

The default write strategy (used unchanged here) repartitions the data into blocks of 8,192 rows, computes zone statistics, applies dictionary layouts where useful, coalesces blocks up to roughly 1 MB of uncompressed data, and compresses each block with BtrBlocks. For the 1M-row columns of this study, that yields chunks of 65,536 to 90,112 rows.

Reading goes through a scan: a projection and an optional filter expression, executed over splits, asynchronously on a Vortex runtime (a current-thread executor here). Filters are pushed down: zone statistics prune whole zones, and comparison kernels can run on compressed data. The scan returns arrays that are still compressed, one per chunk. Everything is registered in a VortexSession (encodings, layouts, compute functions, compression schemes, the runtime handle and "editions", the versioned sets of encodings a file may use).

The model is optimized for one access pattern: scan a column (or a filtered subset that Vortex itself can find with its own statistics), chunk by chunk. The pattern of a search engine, where an external index (the posting lists) supplies an arbitrary sorted subset of row ids, has no first-class API.

3.6 Missing values and sparse columns

tantivy separates "which docs have a value" (the column index) from "the values" (the column values). Vortex has no column index: a column is just an array with one row per doc, and missing values are nulls of that array. How those nulls are stored depends on how many there are.

Nullability and validity

Nullability is part of the DType (u64 vs u64?). A nullable array carries a validity, which is one of: NonNullable, AllValid, AllInvalid, or a boolean child array with one bit per row. The values of null rows still exist physically in a plain encoding (they are just ignored), so a dense nullable column costs its values for every row plus one bit per row of validity. That is fine when most rows have a value, and wasteful when few do.

The sparse encoding

For mostly-null (or mostly-identical) data, Vortex uses vortex.sparse: a fill value plus patches, the list of rows that differ from it.

vortex.sparse                      len = number of rows (e.g. 65,536), dtype u64?
├─ fill value                      null   (or the most frequent value)
└─ patches
   ├─ indices                      sorted positions of the rows that differ from the fill,
   │                               narrowed to the smallest integer type (u16 for a 65,536-row
   │                               chunk), then compressed like any integer array
   ├─ values                       the values at those positions, packed densely,
   │                               compressed by their own cascade (bitpacked, ALP, ...)
   └─ chunk offsets (optional)     where the patches of each 1,024-row block start, so a
                                   lookup can jump to the right slice of indices

Only the rows that have a value cost anything; every other row is implicitly the fill value. Positions and values are ordinary Vortex arrays, so BtrBlocks recursively looks for the best encoding of each. For the positions it excludes the schemes that cannot help on sorted unique integers (dictionary, run-end, RLE, sparse).

When BtrBlocks chooses it

The integer sparse scheme of Vortex 0.88 declares itself applicable in two cases, evaluated on the sample the compressor draws from the chunk:

  • more than 90 % of the rows are null: the estimated ratio is rows / non-null rows;
  • or one value accounts for at least 90 % of the non-null rows: that value becomes the fill and only the others are patches.

It explicitly skips when the sample contains no value at all (expecting an all-null chunk to become a constant). Below 90 % nulls, a nullable column is stored densely: values for every row plus a validity bitmap.

Positions stay a plain u16 array: once narrowed to 16 bits, positions that span the whole chunk cannot be bitpacked any smaller, and delta encoding is not in the default cascade. That is exactly what tantivy's optional index does for blocks with fewer than 6,144 values: a sorted list of 16-bit offsets. The values are bitpacked, but FastLanes works in blocks of 1,024 values, so 655 values cost a full 1,024-value block (2.6 kB instead of 1.6 kB). The values array also keeps a (trivial) validity child, because it inherits the nullable dtype of the column.
  • Regular spacing: positions are free. With one value exactly every 100 rows, the positions become a vortex.sequence (base + step, zero bytes). This is the case of the benchmark's sparse input, and the reason Vortex was 30 % smaller than tantivy there. Real data rarely looks like this.
  • 0.1 %: a sampling miss. With 65 values in 65,536 rows, the ~1,024-row sample usually contains no value, so the sparse scheme skips itself. The compressor falls back to a bitpacked array of width 0 with the 65 values as patches, plus a full validity bitmap: 8 kB of validity for 65 values, 137 bytes per value, where sparse would have needed about 300 bytes in total.
  • 30 %: dense storage. Below the 90 % null threshold, the column is bitpacked for every row (nulls included) plus a full validity bitmap: 8.75 bytes per actual value, almost twice what sparse costs at 10 %. tantivy's dense optional blocks (a bitset with rank metadata, and values for the present rows only) do better here.

Reading a sparse array

  • Decompression (execute to canonical) allocates the full chunk, fills it with the fill value, and scatters the patch values into it, building the validity bitmap on the way. The cost is proportional to the chunk length, not to the number of values.
  • One value (execute_scalar) searches the patch indices for the row (using the chunk offsets when present), and returns either the patch value or the fill.
  • The point accessor of section 8 materializes the positions once per chunk, plus a bitset of the rows that have a value. For a row, it tests the bit and only binary-searches the positions when the row has a value. That is why Vortex was faster than tantivy on selective queries over the sparse input, and also why it stays slightly slower than decompression when a sub-aggregation ends up reading every value of the chunk (many binary searches cost more than one scatter).

take on a sparse array

As always in Vortex, array.take(indices) first builds a lazy vortex.dict node whose codes are the requested rows. When that node is executed, the sparse encoding's take kernel runs, and it only touches the patches:

  1. Find which requested rows have a value. Two strategies, chosen per call by comparing the number of patches with the number of requested rows:
    • search (the usual case for small takes): for each requested row, binary-search the sorted patch positions. When the patches carry chunk offsets, the search first jumps to the 1,024-row block of the requested row and only searches inside it;
    • map (when the patches are fewer than five times the requested rows): build a hash map from patch position to value index over all the patches, then probe it for each requested row.
    For every hit it records the row's position in the output and the index of its value among the patch values.
  2. Take the values. The selected patch values are gathered with the take kernel of their own encoding (for bitpacked values, single-value unpacking when few indices fall into a 1,024-value block). This step is itself lazy.
  3. Build the result, which is still compressed:
    • no requested row has a value: a vortex.constant null of the output length;
    • every requested row has a value: just the selected values, without a sparse wrapper;
    • otherwise: a new vortex.sparse array of the output length, with the new positions and the lazily taken values.

For one large gather, this is efficient: work proportional to the requested rows times a logarithm, plus the values that are actually needed. For the access pattern of an aggregation, one call per block of 64 docs, the fixed part dominates: the lazy node and the optimizer, executing the indices into a primitive array, reading the patch positions again (and decompressing them again if they are compressed, as with a sequence), allocating the new positions and value indices, building the result arrays, and in the map strategy hashing every patch of the chunk. Nothing is kept between calls. That is why the take() experiment of section 7.3 was slower than decompressing whole chunks on the sparse input, and why the point accessor of section 8 materializes the positions and a presence bitset once per chunk and reuses them across calls and queries. (Vortex also has a dedicated filter kernel for sparse arrays, which works on the patches in the same way.)

Compared with tantivy

For random sparse positions the two systems converge on the same idea: about 2 bytes per position plus the bitpacked values. tantivy has a fixed policy (sparse codec below 6,144 values per 65,536-doc block, a dense bitset with rank metadata above), Vortex decides per chunk from a sample. Vortex wins when positions have exploitable structure (regular spacing, which the cascade detects), tantivy wins at intermediate densities (10 % to 90 % present) because its dense blocks never store values for missing docs, and at extreme sparsity where Vortex's sampling can miss.

3.7 Using Vortex from Rust

This section walks through the client API with code taken verbatim from vortex-bench/examples/vortex_client_usage.rs, which compiles against Vortex 0.88 and was run to produce the outputs shown. The encoding_tree helper used to print trees is a ten-line function of the study crate that walks array.children().

Session

Everything starts with a VortexSession: the registry of encodings, layouts, compute functions, compression schemes, and the handle of the async runtime used by file I/O. Execution (decompression) goes through an ExecutionCtx created from the session.

// A session registers encodings, layouts, compute functions and the async runtime.
let runtime = CurrentThreadRuntime::new();
let session = VortexSession::default().with_handle(runtime.handle());
let mut ctx = session.create_execution_ctx();

Building and compressing an array

Arrays are built in their canonical form (here a PrimitiveArray from a buffer) and type-erased into an ArrayRef. Compression is an explicit step: BtrBlocksCompressor returns a new ArrayRef with the same DType and length but a different encoding tree.

// 1M uniform integers in [0, 1_000_000): a plain, uncompressed (canonical) array.
let mut rng = StdRng::seed_from_u64(42);
let values: Vec<u64> = (0..1_000_000).map(|_| rng.random_range(0..1_000_000)).collect();
let array: ArrayRef =
    PrimitiveArray::new(Buffer::from(values.clone()), Validity::NonNullable).into_array();
println!("canonical: {} rows, {} bytes, encoding {}", array.len(), array.nbytes(), array.encoding_id());
// BtrBlocks samples the data and picks a cascade of encodings.
let compressor = BtrBlocksCompressor::from_session(&session);
let compressed: ArrayRef = compressor.compress(&array, &mut ctx)?;
println!(
    "compressed: {} bytes, tree {}",
    compressed.nbytes(),
    encoding_tree(&compressed, 3)
);
canonical: 1000000 rows, 8000000 bytes, encoding vortex.primitive
compressed: 2501120 bytes, tree fastlanes.bitpacked

8 MB of uniform integers below one million become 2.5 MB of 20-bit bitpacking.

slice

slice(range) returns a view on a range of rows. It never copies data. Encodings that know how to slice themselves push the slice down: a bitpacked array just records a new offset into its packed buffer, so the result is still a fastlanes.bitpacked array. Encodings that cannot are wrapped in a lazy vortex.slice node (the encoding tables of section 6 show vortex.slice(vortex.alprd(...)) chunks: views on a larger compressed array).

// slice() is lazy and cheap: on a bitpacked array it only adjusts an offset.
let sliced: ArrayRef = compressed.slice(1_000..1_010)?;
println!("slice: len {}, tree {}", sliced.len(), encoding_tree(&sliced, 3));
slice: len 10, tree fastlanes.bitpacked

filter

filter(mask) keeps the rows selected by a Mask, Vortex's selection type (built from indices, from ranges, or from a bitmap). The result is lazy: a vortex.filter node over the untouched compressed child. The work happens at execution, where an encoding-specific kernel can filter compressed data directly, or the child is decoded and filtered.

// filter() takes a Mask (a set of selected rows) and is lazy too.
let mask = Mask::from_indices(compressed.len(), [3, 17, 500_000, 999_999]);
let filtered: ArrayRef = compressed.filter(mask)?;
println!("filter: len {}, tree {}", filtered.len(), encoding_tree(&filtered, 3));
filter: len 4, tree vortex.filter(fastlanes.bitpacked)

take

take(indices) gathers rows by position; the indices are themselves an array, may repeat and need not be sorted. Internally, Vortex expresses a take as a dictionary array whose codes are the indices and whose values are the original array, then lets its optimizer rewrite the tree. Here the result is vortex.dict(vortex.primitive, fastlanes.bitpacked): still nothing decoded.

// take() gathers rows by index; the indices are themselves an array.
let indices: ArrayRef =
    PrimitiveArray::new(Buffer::<u32>::from(vec![999_999u32, 3, 3, 42]), Validity::NonNullable)
        .into_array();
let taken: ArrayRef = compressed.take(indices)?;
println!("take: len {}, tree {}", taken.len(), encoding_tree(&taken, 3));
take: len 4, tree vortex.dict(vortex.primitive, fastlanes.bitpacked)

Execution

Lazy arrays become values when they are executed into a canonical form. For the take above, execution runs the bitpacked take kernel (which unpacks single values when few indices fall into a 1,024-value block, and whole blocks otherwise) and produces a plain PrimitiveArray.

// Nothing is decoded until the array is executed into a canonical form.
let decoded: PrimitiveArray = taken.execute(&mut ctx)?;
let decoded_values: &[u64] = decoded.as_slice::<u64>();
assert_eq!(decoded_values, &[values[999_999], values[3], values[3], values[42]]);
println!("take executed: {decoded_values:?}");

let filtered_values: PrimitiveArray = filtered.execute(&mut ctx)?;
assert_eq!(
    filtered_values.as_slice::<u64>(),
    &[values[3], values[17], values[500_000], values[999_999]]
);
take executed: [985204, 405901, 405901, 452622]

Single values

execute_scalar(index) returns a Scalar (a dtype plus a value). It goes through the generic machinery for every call, which is fine for occasional access and too slow for the inner loop of an aggregation (section 8).

// Single value access returns a Scalar (dtype + value). Convenient, not for hot loops.
let scalar = compressed.execute_scalar(123_456, &mut ctx)?;

Files and scans

Writing goes through the session's write options (here the blocking adapter over the current-thread runtime); the default strategy chunks, compresses and adds zone statistics. Reading opens the file and builds a scan. A filter expression is bound to the file's dtype and pushed down: zone statistics skip chunks that cannot match, and comparison kernels can run on compressed data. The scan returns the matching rows, still as Vortex arrays.

// Write the array to an in-memory Vortex file, then scan it with a pushed-down filter.
let mut file_bytes: Vec<u8> = Vec::new();
session
    .write_options()
    .blocking(&runtime)
    .write(&mut file_bytes, array.to_array_iterator())?;
let file = session.open_options().open_buffer(file_bytes.clone())?;
let filter = gt(root(), lit(999_000u64)).bind(file.dtype())?.optimize_recursive()?;
let matching: ArrayRef = file
    .scan()?
    .with_filter(filter)
    .into_array_iter(&runtime)?
    .read_all()?;
let expected = values.iter().filter(|&&value| value > 999_000).count();
println!(
    "file: {} bytes; scan with `value > 999000` returned {} rows (expected {expected})",
    file_bytes.len(),
    matching.len()
);
assert_eq!(matching.len(), expected);

What this means for an integration

The API is pleasant for batch work: build, compress, slice, filter, take, and execute when you need values, with everything staying compressed in between. Two properties matter for a search engine. First, every operation allocates a small node and goes through dynamic dispatch and the optimizer; that overhead is negligible per million rows and significant per 64 docs. Second, nothing in the public API lets you "prepare" an array once for repeated reads at arbitrary positions. The integration therefore uses execute for scans (whole chunks) and its own point accessors for selective reads (section 8).

5.1 Writing: the segment plugin

VortexPlugin owns the vortex extension. Its writer accumulates nothing during indexing: at serialize time (and in merge) it opens the segment's .fast file, which the built-in fast field plugin has just written, and converts every non-JSON column of type u64, i64, f64, date or text:

  • values are converted back from the monotonic mapping to their logical type (i64, f64, timestamp in nanoseconds as a Vortex timestamp extension type), so BtrBlocks can use ALP, DateTimeParts, zig-zag and friends;
  • text columns store the tantivy ordinals as u32, and keep using the tantivy sstable dictionary at query time (a native-string variant is measured for size only);
  • cardinality maps to the type: Full → non-nullable array, Optional → nullable array, Multivalued → List;
  • each column becomes a standalone Vortex file written with the default strategy. The .vortex component is the concatenation of these files, each aligned on 64 bytes, followed by a JSON footer (name, type, cardinality, byte range, min, max).

5.2 Reading: the value source

  • Segment cache. A VortexSegmentCache, shared by all providers of a registry, opens the .vortex component once per segment: it copies each file into a 64-byte aligned buffer, opens it from memory and scans it, keeping the compressed chunks. This is what a segment reader would do in a real integration; the tantivy columnar is cheap to open on every query, Vortex files are not.
  • One source per collector. load_block splits the block of docs into runs (one per chunk). Long, dense runs (scans) decompress the chunk into its canonical array and copy the requested values, converting them to tantivy's monotonic u64. The last 8 decompressed chunks are kept in an LRU, because sub-aggregations revisit chunks.
  • Short or sparse runs use a point accessor, built once per chunk and shared across queries, until the chunk has been read densely enough to be worth decompressing (section 8).
  • Metadata. bounds() returns the min / max computed at write time, term_dictionary() returns the tantivy dictionary of the field, as_column() returns None.

5.3 Three variants of every request

  • columnar: the normal tantivy path, exactly what agg_bench measures.
  • opaque: the same tantivy columns, registered in the ValueSourceRegistry behind a wrapper whose as_column() returns None. It pays the "registered source" penalty with the tantivy codec.
  • vortex: the columns of the .vortex file, registered the same way.

So opaque / columnar measures the cost of the abstraction (lost fast paths), vortex / opaque measures the cost of the storage itself, and their product is vortex / columnar.

Registered fields are the twelve non-JSON fast fields of the benchmark schema: score, score_f64, score_i64, timestamp, timestamp_26_bits, and seven text fields. The JSON field json.mixed_type is always read from the tantivy columnar.

5.4 Implementation versions

The reader went through three versions, all measured on the full suite:

v1
Decompress the chunk that contains the doc; keep only the last decompressed chunk.
v2
Same, with an LRU of 8 decompressed chunks. Fixes the thrashing of sub-aggregations.
v3a

6. Sizes

The comparison is done column by column, on the twelve converted columns. For the tantivy side, "column" means values plus column index (optional or multivalued index), excluding the sstable dictionary of text columns, which the Vortex variant reuses. Dictionaries are reported separately. The .fast file is larger than the sum of the columns because it also contains the JSON field and the dictionaries.

6.1 Totals per index

Three regimes stand out. On one large segment, the formats are within 1 % of each other for full columns, and Vortex is smaller as soon as values are missing or repeated (dense −6 %, sparse −30 %, multivalue −34 %). On many small segments, Vortex is larger (+15 % at 100 segments, ×2.2 at 1,000 segments), because of a fixed cost per file.

6.2 Storage approaches compared

The same data can be laid out in several ways. All the totals below cover the twelve columns including what is needed to turn text ordinals back into terms, so they are directly comparable.

  • B vs A is what the benchmark reads: Vortex for the values, tantivy sstables for the terms. It is never larger than the tantivy columnar on a single segment.
  • C stores strings natively in Vortex and drops the sstable. It is the "pure Vortex" option, and the most expensive one on full and dense data (+22 % and +16 %, all of it on the high-cardinality text columns). On sparse and multivalue data it still comes out smaller than tantivy, but only because the savings on the column index of section 6.5 and 6.6 outweigh the loss on text. Section 6.6 explains the text loss.
  • D removes the file format: the arrays compressed in memory by BtrBlocks, without zone statistics, footer or per-chunk layout. On a 1M-row segment the file format costs nothing measurable; the per-chunk choice of encodings in the file even beats one global compression pass on multivalued data (D is larger than B there because the in-memory compressor does not find the arithmetic sequence of list offsets over the whole array).
  • E stores dates as plain i64 instead of the timestamp extension type: the two date columns double in size. Keeping the logical type is what lets BtrBlocks use DateTimeParts.

6.3 Column by column: full

tantivy chose its bitpacked codec for every column of this benchmark (the only exception is one multivalued text column, stored with the blockwise linear codec). Vortex chose bitpacking too for most columns, and fixed-width bitpacking of the same values costs the same, whoever does it. The differences come from what each system can detect before bitpacking.

  • score, score_i64: uniform integers in [0, 1,000,000): 20 bits per value in both systems (2.44 MB vs 2.45 MB). Nothing more can be done for uniform data.
  • Text ordinals: the width is the logarithm of the dictionary size in both systems: 3 bits for the 7 statuses, 10 bits for 1,000 terms, 18 bits for 150,000 terms, 20 bits for the unique terms. Identical sizes. BtrBlocks does not choose a dictionary encoding here because tantivy's ordinals are already dense.
  • score_f64: log-normal doubles with full-precision mantissas. tantivy bitpacks the monotonic mapping of the doubles (about 56 bits per value); Vortex chooses ALP-RD (a 3-bit dictionary code for the high bits, about 52 bits for the low bits, plus patches). 6.92 MB vs 7.00 MB: neither can compress random mantissas.
  • timestamp: timestamps in seconds that grow with the doc id, plus ±2 h of noise. tantivy stores nanoseconds; its bitpacked codec subtracts the minimum and divides by the GCD (109, the field has second precision), and the remaining five-day range needs 19 bits. Vortex's DateTimeParts stores the day, the second within the day and the sub-second separately. The day is almost constant within a 1,024-row block (a block covers a few minutes), so frame of reference reduces it to nearly nothing; the second within the day needs 17 bits; sub-seconds are a constant. About 17.6 bits per value: Vortex is 8 % smaller, thanks to the per-block adaptivity rather than to the date-specific split.
  • timestamp_26_bits: uniformly random 26-bit second counts. tantivy needs exactly 26 bits after the GCD division. DateTimeParts splits each value into a day (10 bits) and a second within the day (17 bits): 27 bits, so Vortex is 4 % larger. Splitting is a loss when the parts are not more regular than the whole.
  • single_term: a constant. Both systems store a header only (a few kB of Vortex file overhead).

6.4 Column by column: dense (one document without values)

Per-column table

The dense index differs from the full one by a single empty document. In tantivy, that makes every column Optional, so every column pays an optional index: one dense block bitset with rank metadata per 65,536 docs, about 160 kB per column, whatever the number of missing values. In Vortex, nullability is a type property but validity is stored per chunk: most chunks carry no validity at all, and only a few chunks around the empty document carry a (compressed) validity child. Result: −6 % for Vortex, all of it on the index.

6.5 Column by column: sparse (one document in 21 has values)

Per-column table

With 50,000 values over 1,050,000 docs, each 65,536-doc block of tantivy's optional index holds about 3,100 values, below the dense threshold of 6,144, so blocks use the sparse codec: a list of 16-bit offsets, 2 bytes per value. Vortex picks its sparse encoding (a null fill plus patches), and compresses the patch positions as a sequence, because in this generator exactly one document in 21 has values. The positions cost almost nothing, hence −30 %.

This regularity is an artifact of the generator. With randomly placed values (measured in section 3.6), the positions stay a plain u16 array, 2 bytes each, exactly like tantivy's sparse optional blocks, and the gap disappears.

6.6 Column by column: multivalue

Per-column table

The multivalue index is the same data as the full one, except that the first document has two values. tantivy stores a MultiValueIndex for every text and numeric column: about 1.5 MB per column for 1M docs. That is visible on single_term, whose values are all the same and cost nothing, but whose index weighs 1.54 MB. Vortex stores a List, whose offsets are 0, 2, 3, 4, …: an arithmetic sequence in every chunk but the first, encoded as vortex.sequence for free. Hence −34 %.

This is the most favorable case possible for Vortex: on genuinely multivalued data, offsets have to be bitpacked too. The size of tantivy's start offsets column on near-linear data is still worth a look independently of Vortex (the linear codec should handle a sequence with a single +1 step well).

Native strings. The C approach of section 6.2 stores the strings themselves. For low-cardinality text, Vortex's dictionary encoding is as good as ordinals + sstable. For high cardinality it is much worse: text_all_unique_terms takes 14.5 MB natively vs 10.9 MB for ordinals + sstable, and text_many_terms (150,000 distinct terms) 6.1 MB vs 2.3 MB. Two reasons. First, the sstable stores sorted terms once per segment with prefix sharing and block compression, while Vortex compresses each chunk independently, so a chunk-level dictionary of 150,000 terms is repeated in each of the 12 chunks. Second, unsorted strings with random digits (unique_term_<u64>) give FSST little to work with. The per-segment sorted dictionary is a structural advantage of tantivy for text.

6.7 Many small segments

Each Vortex file carries a fixed cost: postscript and footer, the serialized DType, the layout tree, zone statistics, segment alignment. With one file per column and per segment, that cost is paid 12,000 times in the 1,000-segment index. A Vortex file there averages 4.1 kB, while the same column of the same segment takes 1.9 kB in the tantivy columnar: roughly 2.2 kB of fixed cost per file. Writing one struct file per segment (all twelve columns as fields of a struct array) shares the footer, the type and the layout root: the overhead drops from +15 % to +8 % at 100 segments, and from ×2.2 to about ×1.5 at 1,000 segments (extrapolated from the first 100 segments). The remaining overhead is the per-column layout and zone statistics, which Vortex keeps even for 1,000-row columns. The tantivy columnar has a single small footer per segment and no per-zone statistics, so it scales down better.

In practice, segments are merged into large ones, so the single-segment numbers are the most representative of steady state; the small-segment numbers matter for freshly committed, unmerged data.

7. Performance

7.1 Methodology

The benchmark is a copy of benches/agg_bench.rs with the same requests and data. For every request, the three variants (columnar, opaque, vortex) are registered in the same binggan group, so they are interleaved: 32 group iterations, an auto-detected number of calls per sample, median reported. Interleaving matters on this machine: the absolute time of the columnar variant drifts by up to 7 % from one run to the next, but the ratios between variants measured within a run are stable. All ratios in this report are computed within a run, then the median over runs is taken.

Before each group, the request runs once per variant and its result is compared with the columnar result (section 9). Requests rejected by registered sources (multi_terms, composite, top_hits, missing on text: 20 of the 79 requests per input) only appear in the columnar variant.

7.4 The abstraction penalty and the bounds() patch

The opaque variant reads exactly the same bytes through exactly the same codec as the columnar variant; the only difference is that the aggregation code does not see the physical column. On the full input this costs ×1.56 on average and up to ×9.4. The worst cases match the fast paths listed in section 2.4:

  • terms_status_with_date_histogram* and terms_status_with_histogram (×3.6 to ×9.4): the flattened terms × histogram collector needs the raw ColumnValues of two full columns;
  • cardinality_agg_low_card (×3.5): the pre-sized ordinal bitset needs the maximum ordinal;
  • terms_7, terms_zipf_90, terms_all_unique (×2.6 to ×2.9): the dense bucket storages are chosen from the maximum ordinal.

On the other inputs the penalty is smaller (×1.1 to ×1.2) because several of these fast paths require a full column anyway.

Two of these fast paths only read the column maximum, which ValueSource::bounds() already provides, with exactly the same value for physical columns, and whose contract ("global value bounds, for fast paths that need to size something up front") covers the use. 7.6 Selective queries, version by version

v1 kept a single decompressed chunk. Pure scans do not care, but sub-aggregations receive their docs in buffered batches grouped by parent bucket. On the sparse input a batch covers about 43,000 rows, often two chunks, and every bucket of the batch decompressed these chunks again: the sparse average was ×2.87 and some selective requests were 195 times slower than opaque. v2 keeps 8 chunks in an LRU and fixes it.

Point accessors are shared per segment and reference the compressed buffers without copying them; they only materialize validity bitsets, patches and small dictionaries.

8. How selective queries were fixed

This section explains the mechanism, without numbers. The measurements are in section 7.

8.1 Why the straightforward reader is slow

A selective query produces a few docs scattered across the whole segment. In this benchmark, the 1 % filter yields clusters of a handful of consecutive docs every few hundred docs. The collector hands them to the value source 64 at a time, so one block covers thousands of rows.

The first versions of the reader handled every block the same way: find the chunk that contains the doc, decompress the whole chunk into a canonical array, pick the requested values. That is the natural way to use Vortex, and it is ideal for scans. For a selective query it is the worst case: since matching docs are spread everywhere, every chunk is touched at least once, so the reader decompresses the entire column to read a tiny fraction of it. The cost becomes proportional to the size of the column instead of the number of docs, which is exactly the opposite of what the tantivy columnar does.

The obvious alternative, Vortex's take, does not help either. Its kernels are efficient (the bitpacked kernel can unpack single values), but every call goes through the generic machinery: wrap the array in a lazy dictionary node, run the optimizer, dispatch dynamically through the encoding tree, allocate an output array, handle validity, recurse into children. That fixed cost is small in absolute terms, but it is paid for every block of 64 docs, and it ends up in the same range as decompressing the chunk.

8.2 The idea: compile each chunk into a point accessor

The values of a compressed Vortex array are not hidden behind an opaque blob: they are a tree of simple, well-specified encodings, and most of them can produce one value at a given index in constant time if you know their raw buffers and parameters. The fix is to walk the encoding tree of a chunk once, extract exactly what is needed for that, and keep it in a compact structure that mirrors the tree without any of the generic machinery. Call it a point accessor.

Each node of the encoding tree becomes a node of the accessor:

bitpacked
keep the packed words, the bit width, the offset of the first element, and the patches. Reading index i means locating its 1,024-value block and unpacking one value from the FastLanes transposed layout, then checking whether a patch overrides it.
frame of reference
keep the child accessor and the reference of each 1,024-value block; the value is the child value plus the reference of its block.
constant, sequence
closed forms: the constant, or base + i × step.
slice
an index shift into the child.
ALP-RD
keep both children (left codes and right parts), the small left dictionary and the patches. The value is the dictionary entry (or the patched left part) shifted left and OR-ed with the right part, reinterpreted as a double.
DateTimeParts
three children and the time unit; the value is days × 86,400 × unit + seconds × unit + subseconds.
sparse
the sorted patch positions and values, plus the fill value.
zig-zag
the usual decode applied to the child value.
masked
the child only; validity is handled separately.
list
an offsets accessor and an elements accessor; the values of row r are the elements between offsets[r] and offsets[r+1].
anything else
if the sub-array is small (a dictionary, the per-block references), it is decompressed once and stored as a plain buffer. If it is large and unknown, the chunk simply gets no accessor and falls back to decompression.

Validity is resolved at the top, once per chunk, into a plain bitset (or nothing, if the chunk has no nulls). Inner nodes never look at validity: a value read at a null position is garbage that the caller skips.

Accessors produce raw 64-bit words: integers in two's complement (narrow signed types sign-extended so that frame-of-reference arithmetic wraps correctly), doubles as their IEEE bits. The value source converts them to tantivy's monotonic u64 mapping at the very end, the same way it does for decompressed values.

8.3 Built once, shared by every query

Building an accessor costs about as much as touching the chunk's metadata, plus materializing a few small children. It happens lazily, the first time a query needs point access into a given chunk, and the result is stored next to the compressed chunk in the per-segment cache. Every later query on the segment, and every collector of the same query, reuses it. The accessor holds reference-counted handles to the original buffers, so it adds almost no memory: the compressed data is not copied.

8.4 Reading a batch, not a value

A naive accessor would walk the tree once per value: one dynamic dispatch per node, then a branch on the bit width inside the unpacking routine. That overhead is several times the cost of the actual bit manipulation. Instead, the value source passes the whole run of rows down the tree:

  • each node handles the batch in one go: the frame-of-reference node asks its child for all values, then adds the references; ALP-RD fetches all left codes and all right parts, then combines them; and so on;
  • the bitpacked node groups the requested rows by FastLanes block and hands each group to the FastLanes "unpack these indices" routine, which resolves the bit width once per group and then unpacks each value with a few shifts and masks.

The tree is thus traversed once per run of docs, and the per-value cost is close to that of a hand-written bitpacked lookup.

8.5 Choosing between point access and decompression

Point access is not always the right tool. For a scan, decompressing a chunk with vectorized kernels is cheaper per value than any per-value lookup, and the decompressed chunk serves many following blocks. The value source therefore decides per run (the docs of one block that fall into the same chunk):

  • if the chunk is already decompressed (in the LRU of the source), read from it;
  • otherwise, if the run is short, or if it spans many more rows than it has docs, use the point accessor;
  • otherwise (a long, dense run, typically a scan), decompress the chunk and keep it in the LRU.

Those rules look at one run at a time, and that is not enough. Under a high-cardinality terms aggregation, a sub-aggregation over the whole segment receives a myriad of runs of one or two docs: every run looks sparse, yet in the end every value of every chunk is read. Reading them all point by point is slower than decompressing each chunk once. The reader therefore keeps, per chunk, a running cost of the point reads already done: a cost per value plus a fixed cost per run. When that cost reaches a fraction of what decompressing the chunk would cost, the chunk is decompressed, put in the LRU, and all later reads come from there. This is the classic "ski rental" strategy: rent while renting is cheaper than buying, then buy. A selective query stays below the threshold and never decompresses anything; a dense pattern made of tiny runs pays a bounded price before switching to decompression.

The "short run" rule came from profiling. The first version only looked at density, and a selective query still spent half of its time decompressing chunks. The reason: matching docs come in small clusters of consecutive docs, and when a block straddles a chunk boundary, the part that falls into the next chunk is often a single cluster. A cluster of four consecutive docs has a perfect density, so the reader decided that it was looking at a scan and decompressed the whole chunk. Requiring a minimum run length before decompressing fixed it.

8.6 Correctness and limits

The decode micro-benchmark compares a checksum of every value read through Vortex with the same checksum read through the tantivy columnar, for every column, every input and both access patterns, and the full aggregation suite compares every aggregation result with the columnar one. Both agree.

The approach has clear limits:

  • It depends on the internal representation of each encoding: the FastLanes transposed layout, the semantics of patches and their offsets, how ALP-RD combines its parts, how frame-of-reference stores one reference per block. These are not public contracts, and Vortex changes quickly; a production version would need either a pinned Vortex version with tests, or, better, an equivalent API upstream.
  • Composite encodings stay more expensive than a single bitpacked lookup: ALP-RD and DateTimeParts read two or three children per value.
  • Encodings that are not random-access by nature (zstd, pco, delta, run-end without an index) cannot be supported this way. BtrBlocks did not pick them for these columns, but it could for other data, and those chunks would fall back to decompression.
  • The thresholds (minimum run length, density ratio, promotion costs, LRU size) are fixed constants tuned on this benchmark. The promotion rule uses the same costs for every encoding, while a point read into a sparse chunk is relatively expensive and decompressing it is cheap; this is why sub-aggregations on sparse data are still slightly slower than with pure chunk decompression. Costs per encoding, or measured at accessor construction, would remove most of that trade-off.

What Vortex would need to support search-engine workloads natively is a cheap, reusable gather primitive: "prepare this array for repeated reads at sorted indices", returning a lightweight object whose per-call cost is a function of the number of indices only. The accessor built here is a prototype of that API, living outside Vortex.

Before each benchmark group, the request runs once per variant and the JSON result is compared with the columnar result.

  • Vortex and opaque always return exactly the same result (same hash) on every request and every input. The Vortex copy of the columns is faithful.

10. Limitations and threats to validity

  • Synthetic data. The agg_bench generator is built to stress aggregations, not storage. Some of its patterns are unrealistically regular (the sparse index has values on exactly one doc in 21; the multivalue index has a single doc with two values), which flatters Vortex on size. Others are unrealistically random (uniform integers, log-normal doubles with full mantissas, random unique strings), which leaves no room to either system. Real logs have more structure: repeated hosts and services, monotonic timestamps, small integer ranges, which is where an adaptive compressor can gain more.
  • Default write strategy. Vortex was used with its default file layout. Chunk sizes, zone sizes and the dictionary layout are tunable, and one struct file per segment already helps small segments.
  • Text as ordinals. The benchmark reads Vortex ordinals and tantivy dictionaries. A pure Vortex design would need its own term resolution, and would lose the sorted-dictionary properties tantivy relies on (ordinals ordered like terms, one dictionary per segment).
  • One machine, single thread. All numbers come from one Apple M4 Max. Ratios between variants are stable (they are measured interleaved), absolute times are not portable.
  • Glue code quality. The value source, the caches and the accessor are a few hundred lines written for this study. Part of the remaining gap on full columns is the copy from the decompressed chunk into the output block, which a deeper integration could avoid.
  • Vortex version. Vortex 0.88 is evolving quickly; APIs used here (especially encoding internals) may change.

11. Recommendations

  • Make aggregation fast paths independent of as_column(). This is the largest lever and it does not depend on Vortex: every computed or external source benefits. bounds() is enough for the terms storage choice and the cardinality bitset (two lines, measured in section 7.4). The flattened terms × histogram collector, the one-doc stats shortcut and the single-value specializations of histograms and ranges need a cardinality hint and a way to read a block of a full column without copying.
  • If Vortex is pursued, pursue it with a point / gather reader like the one of section 8, ideally upstreamed into Vortex as a public API, and with one struct file per segment. Expect parity or better on optional and multivalued columns and on sparse data, a modest cost on full-column scans, and a remaining cost on selective queries over floats and dates.
  • Keep tantivy's sorted dictionary for text. Native Vortex strings are larger on high-cardinality text and lose the ordinal ordering.
  • Size wins are data dependent. On this benchmark, the clear wins (sparse, multivalue) come from Vortex detecting regular structure that the tantivy optional and multivalued indexes do not exploit. Two cheap experiments inside tantivy would capture part of it: compressing the multivalue start offsets better on near-linear data, and storing optional indexes with long runs more compactly.
  • Validate on real data. The next useful measurement is the same pipeline on a real log corpus, where repeated values and monotonic fields are common.
