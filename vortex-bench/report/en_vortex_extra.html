3.6 Missing values and sparse columns

tantivy separates "which docs have a value" (the column index) from "the values" (the column values). Vortex has no column index: a column is just an array with one row per doc, and missing values are nulls of that array. How those nulls are stored depends on how many there are.

Nullability and validity

Nullability is part of the DType (u64 vs u64?). A nullable array carries a validity, which is one of: NonNullable, AllValid, AllInvalid, or a boolean child array with one bit per row. The values of null rows still exist physically in a plain encoding (they are just ignored), so a dense nullable column costs its values for every row plus one bit per row of validity. That is fine when most rows have a value, and wasteful when few do.

The sparse encoding

For mostly-null (or mostly-identical) data, Vortex uses vortex.sparse: a fill value plus patches, the list of rows that differ from it.

vortex.sparse                      len = number of rows (e.g. 65,536), dtype u64?
├─ fill value                      null   (or the most frequent value)
└─ patches
   ├─ indices                      sorted positions of the rows that differ from the fill,
   │                               narrowed to the smallest integer type (u16 for a 65,536-row
   │                               chunk), then compressed like any integer array
   ├─ values                       the values at those positions, packed densely,
   │                               compressed by their own cascade (bitpacked, ALP, ...)
   └─ chunk offsets (optional)     where the patches of each 1,024-row block start, so a
                                   lookup can jump to the right slice of indices

Only the rows that have a value cost anything; every other row is implicitly the fill value. Positions and values are ordinary Vortex arrays, so BtrBlocks recursively looks for the best encoding of each. For the positions it excludes the schemes that cannot help on sorted unique integers (dictionary, run-end, RLE, sparse).

When BtrBlocks chooses it

The integer sparse scheme of Vortex 0.88 declares itself applicable in two cases, evaluated on the sample the compressor draws from the chunk:

  • more than 90 % of the rows are null: the estimated ratio is rows / non-null rows;
  • or one value accounts for at least 90 % of the non-null rows: that value becomes the fill and only the others are patches.

It explicitly skips when the sample contains no value at all (expecting an all-null chunk to become a constant). Below 90 % nulls, a nullable column is stored densely: values for every row plus a validity bitmap.

The values are bitpacked, but FastLanes works in blocks of 1,024 values, so 655 values cost a full 1,024-value block (2.6 kB instead of 1.6 kB).   • Regular spacing: positions are free. With one value exactly every 100 rows, the positions become a vortex.sequence (base + step, zero bytes). This is the case of the benchmark's sparse input, and the reason Vortex was 30 % smaller than tantivy there. Real data rarely looks like this.

  • 0.1 %: a sampling miss. With 65 values in 65,536 rows, the ~1,024-row sample usually contains no value, so the sparse scheme skips itself. The compressor falls back to a bitpacked array of width 0 with the 65 values as patches, plus a full validity bitmap: 8 kB of validity for 65 values, 137 bytes per value, where sparse would have needed about 300 bytes in total.
    • 

  • 30 %: dense storage. Below the 90 % null threshold, the column is bitpacked for every row (nulls included) plus a full validity bitmap: 8.75 bytes per actual value, almost twice what sparse costs at 10 %. tantivy's dense optional blocks (a bitset with rank metadata, and values for the present rows only) do better here.

Reading a sparse array


    

  • Decompression (execute to canonical) allocates the full chunk, fills it with the fill value, and scatters the patch values into it, building the validity bitmap on the way. The cost is proportional to the chunk length, not to the number of values.
    • 

  • One value (execute_scalar) searches the patch indices for the row (using the chunk offsets when present), and returns either the patch value or the fill.
    • 

  • The point accessor of section 8 materializes the positions once per chunk, plus a bitset of the rows that have a value. For a row, it tests the bit and only binary-searches the positions when the row has a value. That is why Vortex was faster than tantivy on selective queries over the sparse input, and also why it stays slightly slower than decompression when a sub-aggregation ends up reading every value of the chunk (many binary searches cost more than one scatter).
    • 



take on a sparse array


As always in Vortex, array.take(indices) first builds a lazy vortex.dict node whose codes are the requested rows. When that node is executed, the sparse encoding's take kernel runs, and it only touches the patches:


    

  1. Find which requested rows have a value. Two strategies, chosen per call by comparing the number of patches with the number of requested rows:
  
      
  
    • search (the usual case for small takes): for each requested row, binary-search the sorted patch positions. When the patches carry chunk offsets, the search first jumps to the 1,024-row block of the requested row and only searches inside it;
      • 
  
    • map (when the patches are fewer than five times the requested rows): build a hash map from patch position to value index over all the patches, then probe it for each requested row.
      • 
  
    
  For every hit it records the row's position in the output and the index of its value among the patch values.
    2. 

  2. Take the values. The selected patch values are gathered with the take kernel of their own encoding (for bitpacked values, single-value unpacking when few indices fall into a 1,024-value block). This step is itself lazy.
    3. 

  3. Build the result, which is still compressed:
  
      
  
    • no requested row has a value: a vortex.constant null of the output length;
      • 
  
    • every requested row has a value: just the selected values, without a sparse wrapper;
      • 
  
    • otherwise: a new vortex.sparse array of the output length, with the new positions and the lazily taken values.
      •

For one large gather, this is efficient: work proportional to the requested rows times a logarithm, plus the values that are actually needed. For the access pattern of an aggregation, one call per block of 64 docs, the fixed part dominates: the lazy node and the optimizer, executing the indices into a primitive array, reading the patch positions again (and decompressing them again if they are compressed, as with a sequence), allocating the new positions and value indices, building the result arrays, and in the map strategy hashing every patch of the chunk. Nothing is kept between calls. That is why the take() experiment of section 7.3 was slower than decompressing whole chunks on the sparse input, and why the point accessor of section 8 materializes the positions and a presence bitset once per chunk and reuses them across calls and queries. (Vortex also has a dedicated filter kernel for sparse arrays, which works on the patches in the same way.)


Compared with tantivy


For random sparse positions the two systems converge on the same idea: about 2 bytes per position plus the bitpacked values. tantivy has a fixed policy (sparse codec below 6,144 values per 65,536-doc block, a dense bitset with rank metadata above), Vortex decides per chunk from a sample. Vortex wins when positions have exploitable structure (regular spacing, which the cascade detects), tantivy wins at intermediate densities (10 % to 90 % present) because its dense blocks never store values for missing docs, and at extreme sparsity where Vortex's sampling can miss.





3.7 Using Vortex from Rust




This section walks through the client API with code taken verbatim from vortex-bench/examples/vortex_client_usage.rs, which compiles against Vortex 0.88 and was run to produce the outputs shown. The encoding_tree helper used to print trees is a ten-line function of the study crate that walks array.children().


Session


Everything starts with a VortexSession: the registry of encodings, layouts, compute functions, compression schemes, and the handle of the async runtime used by file I/O. Execution (decompression) goes through an ExecutionCtx created from the session.








Building and compressing an array


Arrays are built in their canonical form (here a PrimitiveArray from a buffer) and type-erased into an ArrayRef. Compression is an explicit step: BtrBlocksCompressor returns a new ArrayRef with the same DType and length but a different encoding tree.












8 MB of uniform integers below one million become 2.5 MB of 20-bit bitpacking.


slice


slice(range) returns a view on a range of rows. It never copies data. Encodings that know how to slice themselves push the slice down: a bitpacked array just records a new offset into its packed buffer, so the result is still a fastlanes.bitpacked array. Encodings that cannot are wrapped in a lazy vortex.slice node (the encoding tables of section 6 show vortex.slice(vortex.alprd(...)) chunks: views on a larger compressed array).










filter


filter(mask) keeps the rows selected by a Mask, Vortex's selection type (built from indices, from ranges, or from a bitmap). The result is lazy: a vortex.filter node over the untouched compressed child. The work happens at execution, where an encoding-specific kernel can filter compressed data directly, or the child is decoded and filtered.










take


take(indices) gathers rows by position; the indices are themselves an array, may repeat and need not be sorted. Internally, Vortex expresses a take as a dictionary array whose codes are the indices and whose values are the original array, then lets its optimizer rewrite the tree. Here the result is vortex.dict(vortex.primitive, fastlanes.bitpacked): still nothing decoded.










Execution


Lazy arrays become values when they are executed into a canonical form. For the take above, execution runs the bitpacked take kernel (which unpacks single values when few indices fall into a 1,024-value block, and whole blocks otherwise) and produces a plain PrimitiveArray.










Single values


execute_scalar(index) returns a Scalar (a dtype plus a value). It goes through the generic machinery for every call, which is fine for occasional access and too slow for the inner loop of an aggregation (section 8).










Files and scans


Writing goes through the session's write options (here the blocking adapter over the current-thread runtime); the default strategy chunks, compresses and adds zone statistics. Reading opens the file and builds a scan. A filter expression is bound to the file's dtype and pushed down: zone statistics skip chunks that cannot match, and comparison kernels can run on compressed data. The scan returns the matching rows, still as Vortex arrays.










Building a sparse column


Nullable arrays can be built from an iterator of Option; the compressor then chooses the sparse representation by itself.










What this means for an integration


The API is pleasant for batch work: build, compress, slice, filter, take, and execute when you need values, with everything staying compressed in between. Two properties matter for a search engine. First, every operation allocates a small node and goes through dynamic dispatch and the optimizer; that overhead is negligible per million rows and significant per 64 docs. Second, nothing in the public API lets you "prepare" an array once for repeated reads at arbitrary positions. The integration therefore uses execute for scans (whole chunks) and its own point accessors for selective reads (section 8).
